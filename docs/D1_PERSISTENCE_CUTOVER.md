# GATE D1 persistence: staged cutover and recovery

## Scope and authoritative baseline

The operator independently verified 206 original `records` rows against identical staging copies: 25 buses, 16 dorms, 16 archives, 2 configuration records and 147 sound events. Ten `gate_*` tables were present; the five new feature tables had no data. Active configuration `week_group` was `WG26050` at verification. Two distinct historical archives have the label `WG26047`; the lifecycle therefore uses an internal `cycle_id` and does not impose display-label uniqueness.

**Do not assume these counts are current.** Normal operations can change production after verification. The original `records` table remains retained as an authoritative write path and rollback source throughout this release. Nothing in a GitHub merge automatically updates remote D1 or configures its `DB` binding.

## Migration plan (operator-controlled, not automated by this PR)

1. Obtain a verifiable independent backup of remote D1 before any migration or flag change; the dashboard SQL console accepts SQL only, not `npx` commands. Confirm the project's actual Cloudflare D1 binding name `DB`, deployment and database identity without guessing a database ID.
2. Coordinate a short period with no operational writes. Re-run the full six-column parity query: original count, mirror count, missing, different, extra, unmapped must agree with four zeros. Confirm active `records` configuration and dorms refer to the same actual Week Group.
3. Check `sqlite_master` for existing mirror triggers. If not already present, apply versioned `migrations/0003_gate_persistence_foundation.sql` to the intended D1 database through an approved migration method. This script uses `IF NOT EXISTS` and never drops or backfills rows. It adds missing old audit protections and three record-mirror triggers. It is not safe to assume migrations were registered in `d1_migrations` simply because tables were manually created.
4. Apply `migrations/0004_gate_record_audit_triggers.sql` to establish atomic, append-only audit events for subsequent record create/update/delete; do not fabricate audit history for pre-migration mutations.
5. Repeat the full parity check after both migrations and a controlled non-sensitive test write if authorized. Confirm all three mirror triggers, three record audit triggers, four audit/amendment immutability triggers, and original audit protections. Verify the new five feature tables have not been unexpectedly populated. Keep `GATE_PERSISTENCE_ENABLED` unset/false until all checks pass.
6. Deploy the repository code with the feature flag **off**. Perform an authenticated smoke test of the legacy board, airport, processing, archives, and Input page. A merge alone must not be treated as successful deployment or database activation.
7. In an isolated D1 test deployment, set `GATE_PERSISTENCE_ENABLED=true` with a correctly configured `AUTH_SECRET` and the `DB` binding. Confirm `/api/persistence?mode=health` (instructor session) reports `ready:true`, three mirror triggers and zero parity differences. Exercise draft create/save/conflict/reload; adoption of an existing active cycle; blocked second initialization; atomic initialization, operations/audit records, closeout and archive preservation; interruptions/retries; stale/offline UI and read-only roles. Check historical archives and mobile access. Fail the rollout if a test is incomplete.
8. For production activation, recheck remote parity and active WG after the quiet window. Enable the flag only after verifying operational coverage and a backup. The UI will require an instructor to **register the currently active legacy Week Group**; this must not create or clear dorm/bus records. When the active group is closed through the new endpoint, archive creation and live clear commit atomically. New initialization consumes a saved Input draft atomically.
9. Preserve the original table after cutover. Typed `gate_v2_*` tables are maintained by same-transaction triggers; avoid writing to them manually or using them as a competing independent write authority. Investigate discrepancies before enabling or re-enabling operations. Do not run `INSERT OR REPLACE`, truncate, delete archives, or impose uniqueness on displayed Week Group labels.

## Runtime switches and rollback

`GATE_PERSISTENCE_ENABLED` is opt-in; when absent or not exactly `true`, the new endpoint refuses mutations and the browser adapter leaves the legacy UI alone. This permits deploying dormant code first. A missing `AUTH_SECRET` blocks persistence operations. If activation fails, turn the flag off and redeploy/refresh after assessing active lifecycle state; do not blindly replay legacy initialization/closeout if a request may already have committed. Check the saved operation idempotency record, active cycle and archive first. The legacy controller cannot safely resume an ambiguous partial operation without investigation.

`GET /api/persistence?mode=health` is instructor-only and reports parity, trigger count, legacy Week Group, and cycle state; `mode=draft` retrieves a saved draft; `mode=amendments&id=<archive ID>` retrieves correction history. POST actions `save_draft`, `adopt`, `initialize`, `closeout`, `amend_archive` are instructor-only and mutation requests are same-origin checked. A failure response never guarantees an interrupted client request did not commit: re-read authoritative state and use the same idempotent operation identity rather than submitting a different cycle.

## Data and security boundaries

Only the proposed Week Group, configured dorm rows, receiving windows and approved Flight Alert review summary are stored in a draft. Do not store raw uploaded PDFs, trainee names, SSNs, orders or other unnecessary personal data. Browser draft edits are not marked saved until D1 confirms them; offline writes are not queued or replayed. Audit entries retain entity ID, type, role, version and timestamps, not raw operational JSON. Shared instructor credentials identify a role, not an individual person.

The legacy `records` API is still available for day-to-day bus/dorm operations; enabled middleware blocks generic lifecycle modifications, archive mutation and new dorms outside transactional initialization. The typed tables mirror this legacy write path in database triggers; a subsequent dedicated scoped read API can take over after production parity/performance measurement. The archive snapshot is immutable after activation and correction requests append amendment records instead of overwriting it. The existing Squadron sign-in and board redesign are separate from this persistence cutover; do not claim those are delivered by these migrations.

## Acceptance and non-goals

Pass criteria: exact source/mirror parity; single live cycle; draft recovery and stale-save rejection; initialization creates no partial rows after failure; archive + cleanup commit atomically; old archive history and role access retained; audit events append-only; no new independently mutable sources of truth. The repo's SQLite tests run against fixtures, **not** the live remote D1 database. No automatic production migration, backup/export, secret creation, D1 binding change, URL/domain change or Cloudflare deployment is performed by the PR.
