# GATE D1 persistence: staged cutover and recovery

## Scope and authoritative baseline

The operator independently verified 206 original `records` rows against identical staging copies: 25 buses, 16 dorms, 16 archives, 2 configuration records and 147 sound events. Ten `gate_*` tables were present; the five new feature tables had no data. Active configuration `week_group` was `WG26050` at verification. Two distinct historical archives have the label `WG26047`; the lifecycle therefore uses an internal `cycle_id` and does not impose display-label uniqueness.

**Do not assume these counts are current.** Normal operations can change production after verification. The original `records` table remains retained as an authoritative write path and rollback source throughout this release. Nothing in a GitHub merge automatically updates remote D1 or configures its `DB` binding.

## Migration plan (operator-controlled, not automated by this PR)

1. Obtain a verifiable independent backup of remote D1 before any migration or flag change; the dashboard SQL console accepts SQL only, not `npx` commands. Confirm the project's actual Cloudflare D1 binding name `DB`, deployment and database identity without guessing a database ID.
2. Coordinate a short period with no operational writes. Re-run the full six-column parity query: original count, mirror count, missing, different, extra, unmapped must agree with four zeros. Confirm active `records` configuration and dorms refer to the same actual Week Group.
3. Check `sqlite_master` for existing mirror triggers. If not already present, apply versioned `migrations/0003_gate_persistence_foundation.sql` to the intended D1 database through an approved migration method. This script uses `IF NOT EXISTS` and never drops or backfills rows. It adds missing old audit protections and three record-mirror triggers. It is not safe to assume migrations were registered in `d1_migrations` simply because tables were manually created.
4. Apply `migrations/0004_gate_record_audit_triggers.sql` to establish atomic, append-only audit events for subsequent record create/update/delete; do not fabricate audit history for pre-migration mutations.
5. Repeat the full parity check after both migrations and a controlled non-sensitive test write if authorized. Confirm all three mirror triggers, three record audit triggers, four audit/amendment immutability triggers, and original audit protections. Verify the new five feature tables have not been unexpectedly populated. Keep both `GATE_PERSISTENCE_ENABLED` and `GATE_PERSISTENCE_CUTOVER_READY` unset/false until all checks pass.
6. Deploy the repository code with the feature flag **off**. Perform an authenticated smoke test of the legacy board, airport, processing, archives, and Input page. A merge alone must not be treated as successful deployment or database activation.
7. In isolated staging D1, use an Instructor session to call the **read-only** `GET /api/persistence?mode=cutover_preflight` before setting either flag. Require `ready:true`, `missing_tables:[]`, `missing_triggers:[]`, `invalid_triggers:[]`, zero source/mirror differences, no extra/unmapped records, and consistent active configuration and lifecycle. If this returns `ready:false` or a 503, do not enable transactional cutover; reconcile the source, schema and triggers in staging first. This endpoint is a runtime D1 check, not proof of production migration history or exact SQL schema equivalence.
8. Stage the **two-step switch**: set `GATE_PERSISTENCE_ENABLED=true` while `GATE_PERSISTENCE_CUTOVER_READY` is unset/false. Legacy atomic initialization and closeout **must still work**; staged save/adopt/initialize/closeout must return 503. Only after successful staging preflight and operator acceptance, set `GATE_PERSISTENCE_CUTOVER_READY=true`. Reload authenticated Instructor/Admin pages and verify the served HTML includes **exactly one** `/js/gate-persistence-runtime.js` loaded after the legacy controllers; the legacy-only state must have zero copies. Health must now show `enabled:true,ready:true`. Exercise D1 draft create/save/conflict/reload, legacy active-cycle adoption (without re-creating dorms), atomic initialization, single verified closeout, loss/timeout reconciliation, cross-device conflicts, read-only roles and historical reports. Trigger deliberate parity failure in isolated D1: the staged adapter must block lifecycle writes, not silently fall back. Do not activate if any test is incomplete.
8a. Production cutover requires a current verified independent backup, a no-write window, read-only preflight on the **actual intended remote DB binding**, explicit operator authorization, and a fresh HTML/runtime smoke test. Enable the two settings in sequence, never only the second one. Old browser sessions must reload before Week Group lifecycle operations. Adopt an existing active legacy group through the staged controller, without clearing or recreating live records. After cutover, original `records` remains the operational write authority with typed mirrors maintained by database triggers.
9. Preserve the original table after cutover. Typed `gate_v2_*` tables are maintained by same-transaction triggers; avoid writing to them manually or using them as a competing independent write authority. Investigate discrepancies before enabling or re-enabling operations. Do not run `INSERT OR REPLACE`, truncate, delete archives, or impose uniqueness on displayed Week Group labels.

## Runtime switches and rollback

A single `GATE_PERSISTENCE_ENABLED=true` setting is **not** a cutover. The staged lifecycle becomes active only when **both** `GATE_PERSISTENCE_ENABLED=true` and `GATE_PERSISTENCE_CUTOVER_READY=true`. This identical authorization check is used by the Input initialization API, legacy closeout, generic operational-write guard, and served HTML script injector. Before both are true, the existing legacy Input and Closeout controllers and endpoints remain available; the staged browser runtime is absent. The second switch must never be enabled without a verified D1 preflight, deployed runtime asset and test approval. The server repeats readiness checks on transactional commands and generic operational writes; failures block writes instead of creating partial cycles.

`GET /api/persistence?mode=cutover_preflight` is read-only and can be called with both flags off. It checks required 10 gate tables, 12 protected trigger names/bodies, source/mirror row parity, unmapped/extra rows, active Week Group configuration and lifecycle consistency. `GET /api/persistence?mode=health` describes the **effective authorized** runtime state; with one flag only it returns `enabled:false`. `mode=draft` retrieves a saved draft after authorization. `mode=amendments&id=<archive ID>` retains its independently guarded append-only correction behavior. Atomic `initialize_legacy` runs only before full cutover; `save_draft`, `adopt`, `initialize`, and `closeout` require both flags **and** server readiness. An archive amendment requires existing append-only D1 safeguards, independently of these flags; Admin amendment provenance requires migration 0007.

**Rollback cannot be blind.** If the new lifecycle has already registered an active `gate_week_groups` cycle, disabling the second flag will restore legacy routing but **legacy closeout will still refuse** to close that registered cycle; that is deliberate protection against destroying transactional state. In that case reconcile the cycle/operation history and complete or recover the transactional closeout under controlled authorization before returning to legacy mode. Never re-run initialization or closeout under another request ID after an uncertain response. Inspect the original record, operation identity, archive, active configuration and D1 parity first. An absent `AUTH_SECRET` or `DB` must block staged operations.

## Data and security boundaries

Only the proposed Week Group, configured dorm rows, receiving windows and approved Flight Alert review summary are stored in a draft. Do not store raw uploaded PDFs, trainee names, SSNs, orders or other unnecessary personal data. Browser draft edits are not marked saved until D1 confirms them; offline writes are not queued or replayed. Audit entries retain entity ID, type, role, version and timestamps, not raw operational JSON. Shared instructor credentials identify a role, not an individual person.

The legacy `records` API is still available for day-to-day bus/dorm operations; enabled middleware blocks generic lifecycle modifications, archive mutation and new dorms outside transactional initialization. The typed tables mirror this legacy write path in database triggers; a subsequent dedicated scoped read API can take over after production parity/performance measurement. The archive snapshot is immutable after activation and correction requests append amendment records instead of overwriting it. The existing Squadron sign-in and board redesign are separate from this persistence cutover; do not claim those are delivered by these migrations.

## Acceptance and non-goals

Pass criteria: exact source/mirror parity; single live cycle; draft recovery and stale-save rejection; initialization creates no partial rows after failure; archive + cleanup commit atomically; old archive history and role access retained; audit events append-only; no new independently mutable sources of truth. The repo's SQLite tests run against fixtures, **not** the live remote D1 database. No automatic production migration, backup/export, secret creation, D1 binding change, URL/domain change or Cloudflare deployment is performed by the PR.
